The npx appium-mcp@latest entry in .mcp.json looked correct and still timed out. Here's what was actually happening, and the config that replaced it.

[fix] Install it this way

[fix] Cài theo cách này

  1. Install the server globally instead of launching it through npx. Cài server này ở phạm vi toàn cục, không chạy qua npx. 
    npm install -g appium-mcp@1.92.0
  2. Confirm where the binary landed. Kiểm tra xem file thực thi nằm ở đâu. 
    where appium-mcp
C:\nvm4w\nodejs\appium-mcp
C:\nvm4w\nodejs\appium-mcp.cmd

    Your path will differ depending on which Node install owns your global npm prefix. Whatever where appium-mcp reports is the binary .mcp.json needs to point at.

    Đường dẫn của bạn có thể khác, tùy vào bản Node nào đang giữ npm prefix toàn cục. Cứ dùng đúng kết quả mà where appium-mcp trả về để điền vào .mcp.json.

  3. Point .mcp.json at that binary directly. Chỉnh .mcp.json để gọi trực tiếp file thực thi đó.
    .mcp.json 
    {
  "mcpServers": {
    "appium-mcp": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "appium-mcp@latest"],
      "command": "appium-mcp.cmd",
      "args": [],
      "env": {}
    }
  }
}
  4. Reconnect. Kết nối lại. 
    > /mcp
Reconnected to appium-mcp.

[why] What the old config was actually waiting on

[why] Cấu hình cũ thật ra đang chờ cái gì

The failure read as a broken package or a bad config. It was neither: npm view appium-mcp version resolved fine, and the tarball was already sitting in the npm cache. Running the exact command from .mcp.json by hand even started clean and answered a real MCP initialize handshake correctly. So the package was never the problem.

Lỗi trông như gói hỏng hoặc cấu hình sai, nhưng không phải cả hai: npm view appium-mcp version vẫn phân giải được, và file tarball đã có sẵn trong cache của npm. Chạy đúng lệnh trong .mcp.json bằng tay còn khởi động sạch sẽ và trả lời đúng cho một cuộc bắt tay initialize thật của MCP. Vậy gói không hề là vấn đề.

The gap was npx itself. It caches its resolution by the exact spec string, not by package name: appium-mcp@latest and appium-mcp@1.92.0 are two separate cache entries, even though they're the same code. The first time either spec runs, npx makes a registry round trip to resolve it before the process starts, and a stdio MCP server hasn't spawned yet while that's happening. That round trip is what a client's connect timeout is racing against.

Điểm nghẽn là npx chính nó. Nó lưu cache theo đúng chuỗi spec, không theo tên gói: appium-mcp@latest và appium-mcp@1.92.0 là hai mục cache khác nhau, dù cùng một mã nguồn. Lần đầu chạy một spec bất kỳ, npx phải gọi ra registry để phân giải trước khi tiến trình khởi động, và một MCP server dạng stdio thì chưa hề được sinh ra trong lúc đó. Chính khoảng chờ đó là thứ đang đua với thời gian chờ kết nối của client.

To check, this session forced a cold spec on purpose: npx appium-mcp@1.92.0, a version string it had never resolved before. That hung twice in a row, killed at 20s, then again at 30s. The exact same package via appium-mcp@latest, already resolved earlier in the session, started in 3 seconds. Same code, same machine, same network: the only variable was whether npx had resolved that spec before.

Để kiểm tra, session này cố tình ép một spec "lạnh": npx appium-mcp@1.92.0, một chuỗi phiên bản chưa từng được phân giải trước đó. Nó treo hai lần liên tiếp, dừng ở 20 giây, rồi lại 30 giây. Cùng gói đó gọi qua appium-mcp@latest, vốn đã được phân giải từ trước trong session, khởi động trong 3 giây. Cùng mã nguồn, cùng máy, cùng mạng: biến số duy nhất là npx đã từng phân giải spec đó hay chưa.

npx @latest (warm) npx @latest (đã phân giải) 3s
npx @1.92.0, run 1 npx @1.92.0, lần 1 >20s
npx @1.92.0, run 2 npx @1.92.0, lần 2 >30s
global binary binary toàn cục <1s

Striped bars didn't finish: both cold runs were still hanging when killed, so >20s and >30s are lower bounds, not actual durations.

Các thanh có vân sọc là chưa chạy xong: cả hai lần chạy "lạnh" vẫn đang treo lúc bị dừng, nên >20 giây và >30 giây là mốc tối thiểu, không phải thời gian thực tế.

One more factor stacked on top: this machine starts roughly 50 concurrent node.exe processes at session start for every other configured MCP server. That contention doesn't cause the timeout by itself, but it shortens the margin a slow registry lookup had to work with.

Có thêm một yếu tố cộng dồn: máy này khởi động khoảng 50 tiến trình node.exe đồng thời khi vào session, cho tất cả các MCP server khác đã cấu hình. Sự tranh chấp đó không tự nó gây ra timeout, nhưng nó làm co lại khoảng dư mà một lượt tra cứu registry chậm cần để hoàn tất.

[verify] How this was confirmed, not assumed

[verify] Đã xác nhận thế nào, không chỉ đoán

  • Sent a real MCP initialize request over stdin to the running process and read back a valid JSON-RPC response (serverInfo named MCP Appium, version 1.92.0) before touching the config.
  • Gửi một yêu cầu initialize thật của MCP qua stdin tới tiến trình đang chạy và đọc lại được phản hồi JSON-RPC hợp lệ (serverInfo tên MCP Appium, phiên bản 1.92.0) trước khi chạm vào cấu hình.
  • Ran the global binary standalone and diffed its startup log line-for-line against the npx version: identical, including the harmless [FastMCP warning] could not infer client capabilities line, which turned out to be cosmetic in both cases.
  • Chạy binary toàn cục một mình và so từng dòng log khởi động với bản chạy qua npx: giống hệt, kể cả dòng cảnh báo vô hại [FastMCP warning] could not infer client capabilities, hóa ra chỉ là hình thức ở cả hai trường hợp.
  • Only after both of those checks passed did .mcp.json get edited, and /mcp reported Reconnected to appium-mcp. on the first try.
  • Chỉ sau khi cả hai bước trên đều ổn mới sửa .mcp.json, và /mcp báo Reconnected to appium-mcp. ngay lần đầu.

[if it recurs] Where to look next time

[if it recurs] Lần sau thì tìm ở đâu

  • Suspect npx's cold-resolution round trip first for any npx ...@latest entry in .mcp.json, not just this one. The same fix (global install, direct binary path) applies to each.
  • Với mọi mục dùng npx ...@latest trong .mcp.json, không riêng gói này, nghi trước tiên là lượt phân giải "lạnh" của npx. Cách sửa giống nhau: cài toàn cục, chỉ thẳng vào file thực thi.
  • A timeout error means something started but didn't finish the handshake in time. That's a different failure than a spawn error (bad path, missing binary), which surfaces immediately instead.
  • Lỗi timeout nghĩa là có gì đó đã bắt đầu chạy nhưng không kịp hoàn tất bắt tay. Khác với lỗi khởi tạo tiến trình (sai đường dẫn, thiếu file thực thi), loại lỗi đó hiện ra ngay lập tức.
  • If appium-mcp gets reinstalled or upgraded, re-run where appium-mcp. The global prefix can move if the active Node version changes.
  • Nếu appium-mcp được cài lại hoặc nâng cấp, chạy lại where appium-mcp, vì npm prefix toàn cục có thể đổi nếu bản Node đang dùng thay đổi.
