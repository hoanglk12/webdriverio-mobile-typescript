01

What the app is, and why this was captured live

FrontRow is a live-events ticketing app. It opens on a list of concerts, lets you filter by genre and search by show, artist, or city, then buy a ticket for an event. Buying a ticket needs a signed-in account; browsing does not.

This catalog was built by driving the installed build directly, because the repo's checked-in LoginPage, HomePage, and their specs model a different, fictional shopping app. Reading them would have produced test cases for screens that do not exist in FrontRow. The screen names, element ids, prices, and status values below are the real ones, read off the live element tree.

03

Findings worth acting on

likely bug

The promo discount never reaches the ticket record

Applying FRONTROW10 takes the Buy Ticket total from ¥950000 down to ¥855000 and shows a discount line. The ticket saved to My Tickets and Ticket Detail records the full ¥950000. The discount looks display-only. This deserves a bug ticket and a standing assertion in the purchase test.

framework mismatch

Sign-in lives behind Profile, not on launch

The app opens on Events with no login gate. Sign-in exists only at Profile, then Sign in. The repo's LoginPage and login.spec.ts assume login is the first screen, so they cannot pass against this build. New page objects for the real screens are the prerequisite for any of the cases below.

automation note

Cancelling a ticket needs a real swipe, not a tap on the hidden id

The Cancel control sits under the ticket row and only appears after swiping the row left. Tapping the row opens Ticket Detail instead. Automation that taps myTickets.swipeCancel.* without swiping first lands on the wrong screen.

behavior

Cancel produces "refund pending", not removal

Confirming a cancel moves the ticket from active to refund pending and keeps it in the list. Tests should assert the status change rather than the ticket disappearing.

correction

The filter chips are All, Indie Rock, Classical, Electronic, Folk

There is no Featured chip. "Featured" is only a badge on one event card. An earlier field note recorded this wrong. There is also a fourth bottom tab, Debug, that was not previously documented.

environment drift

The "All" filter now shows one event, not two

This catalog was captured 9 Aug 2026 with two events under "All" (see SMK-03 and E2E-01, which both assume a second event that disappears/narrows away on search). As of 6 Sep 2026, only events.item.evt_005 ("Zenith Tour — Tokyo Night One", dated Tue Sep 22) remains; the other event is gone from the signed-out default list. Unconfirmed hypothesis: the app only lists upcoming events and the missing one's date has since passed — there is no seed-reset control in the Debug tab to check this directly. SMK-03's implementation (tests/specs/smoke/events.spec.ts) was written catalog-size-agnostic for this reason: it proves the search field actually filters (a nonsense query must return zero results) and then asserts the expected event is present, rather than asserting a fixed before/after count. Any future implementation of E2E-01 step 2 ("confirm two events") should do the same.

automation note

The event list filters live and asynchronously — don't read it right after typing

events.searchInput re-filters events.list on every keystroke with no submit action, but the re-render can lag the driver's setValue response by roughly 1-5s on this device. Reading card count/labels immediately after typing is flaky — it can catch the list mid-filter. EventsPage.waitForEventCount(expected) polls instead of reading once; use it (or the same pattern) for any future search/filter assertion on this screen.

automation note

hideKeyboard() reliably fails on this device and costs ~11s per call

browser.hideKeyboard() throws WebDriverError: The software keyboard cannot be hidden when running "appium/device/hide_keyboard" on this Genymotion image, retried 3x by the WebDriver client before giving up (~11s), then swallowed by BasePage.hideKeyboard()'s own try/catch — so it doesn't fail tests, it just silently burns time and logs an error every call. Root cause unconfirmed (likely this vbox86 image's AOSP keyboard not supporting the ADJUST_RESIZE-based hide strategy). Search filtering and element queries both work fine with the keyboard still showing, so EventsPage.searchEvents() deliberately skips the hide-keyboard step; don't add it back by convention until this is root-caused.
