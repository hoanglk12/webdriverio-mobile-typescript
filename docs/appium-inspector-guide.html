What this covers / Nội dung tài liệu này

Appium Inspector is the GUI for looking at a live Appium session: a screenshot of the device next to the element tree, so locators and gestures can be tried out before any test code gets written. This page covers installing it on Windows, connecting it to this repo's local Appium server, the locator strategies that actually hold up against FrontRow, and the gesture files already sitting in docs/gestures/.

Appium Inspector là công cụ giao diện đồ họa để xem một phiên Appium đang chạy: ảnh chụp màn hình thiết bị đặt cạnh cây phần tử, giúp thử locator và cử chỉ (gesture) trước khi viết bất kỳ đoạn test nào. Tài liệu này trình bày cách cài đặt trên Windows, kết nối với Appium server chạy cục bộ của repo này, các chiến lược locator thực sự đáng tin cậy với FrontRow, và các file gesture đã có sẵn trong docs/gestures/.

Installing it / Cài đặt

Don't run npx appium-inspector. It looks like the fastest way to try it once without installing anything, and it downloads without complaint, but it fails at launch with 'electron' is not recognized as an internal or external command. The npm package published as appium-inspector is a mirror of the project's source tree, not a packaged CLI. Its own package.json does define a bin entry, but it points at ./node_modules/.bin/electron, and electron only appears in devDependencies, which npx never installs. That path never gets created, so the command npx tries to run doesn't exist.

Appium Inspector actually ships as a desktop build, from the GitHub releases of appium/appium-inspector. The win-x64.zip build is portable: no installer, no admin rights, just unzip and run Appium Inspector.exe.

Đừng chạy npx appium-inspector. Nhìn thì có vẻ là cách nhanh nhất để thử mà không cần cài gì cả, và lệnh này tải về không báo lỗi gì, nhưng khi khởi chạy sẽ báo 'electron' is not recognized as an internal or external command. Gói npm mang tên appium-inspector thực chất là bản sao mã nguồn của dự án, không phải một CLI đóng gói. package.json của nó có khai báo trường bin, nhưng trỏ tới ./node_modules/.bin/electron, trong khi electron chỉ nằm trong devDependencies, mà npx không bao giờ cài. Đường dẫn đó không bao giờ được tạo ra, nên lệnh mà npx cố chạy không tồn tại.

Appium Inspector thực ra được phát hành dưới dạng bản build desktop, lấy từ GitHub releases của appium/appium-inspector. Bản win-x64.zip là bản portable: không cần trình cài đặt, không cần quyền admin, chỉ cần giải nén và chạy Appium Inspector.exe.

Starting a session / Bắt đầu một phiên

Point Inspector at a standalone Appium server, not at the appium-mcp MCP server this repo already runs on port 4723. Start one on a separate port:

Trỏ Inspector tới một Appium server độc lập, không phải tới appium-mcp MCP server mà repo này đang chạy ở cổng 4723. Khởi động một server riêng ở cổng khác:

ANDROID_HOME=C:/Android/Sdk npx --no-install appium --address 127.0.0.1 --port 4725 --relaxed-security

In the session builder: Remote Host 127.0.0.1, Remote Port 4725, Remote Path /. Pin appium:udid to the device's current adb address rather than relying on deviceName, since the Genymotion VM's IP has changed before (it moved from .101 to .102 across a VM recreation). The row based capability builder also asks for a type per row (text, boolean, number, or JSON object): everything below is text except noReset and forceAppLaunch, which are boolean.

Trong màn hình tạo phiên: Remote Host là 127.0.0.1, Remote Port là 4725, Remote Path là /. Gắn appium:udid theo địa chỉ adb hiện tại của thiết bị thay vì phụ thuộc vào deviceName, vì IP của máy ảo Genymotion từng thay đổi (từ .101 sang .102 sau khi tạo lại máy ảo). Bộ tạo capability theo từng dòng cũng hỏi kiểu dữ liệu cho mỗi dòng (text, boolean, number, hoặc JSON object): tất cả các dòng dưới đây đều là text, trừ noReset và forceAppLaunch là boolean.

CapabilityTypeValue
platformNametextAndroid
appium:automationNametextUiAutomator2
appium:udidtext192.168.56.102:5555
appium:appPackagetextapp.frontrow.qa

Mistake: the first session opened straight to the device's home screen instead of FrontRow, even with appPackage and appActivity set correctly. The Appium server log had the answer: 'app.frontrow.qa' is already running and noReset is enabled. A previous session had left the app running in the background, and noReset skips relaunching an app it already sees running. Adding appium:forceAppLaunch fixed it: Appium force stopped the stale process and started the app fresh.
Sai lầm gặp phải: phiên đầu tiên mở thẳng vào màn hình chính của thiết bị thay vì FrontRow, dù appPackage và appActivity đã khai báo đúng. Log của Appium server cho câu trả lời: 'app.frontrow.qa' is already running and noReset is enabled. Một phiên trước đó đã để ứng dụng chạy ngầm, và noReset bỏ qua việc khởi chạy lại một ứng dụng mà nó thấy đang chạy. Thêm appium:forceAppLaunch đã xử lý được: Appium buộc dừng tiến trình cũ và khởi chạy lại ứng dụng từ đầu.

Native mode, not Web/Hybrid / Native mode, không phải Web/Hybrid

Leave the mode toggle at the top on Native App Mode (the tree icon, selected by default), not Web/Hybrid App Mode (the globe icon). The Source panel already answers the question: it lists android.widget.FrameLayout and android.widget.LinearLayout nodes, plain native Android views, not a WebView with DOM nodes. React Native compiles down to native widgets unless a screen embeds an actual <WebView> component.

Giữ nút chuyển chế độ ở trên cùng ở Native App Mode (biểu tượng cây, được chọn mặc định), không chuyển sang Web/Hybrid App Mode (biểu tượng quả địa cầu). Panel Source đã trả lời sẵn câu hỏi này: nó liệt kê các node android.widget.FrameLayout và android.widget.LinearLayout, là các view Android gốc thông thường, không phải WebView với node DOM. React Native biên dịch xuống thành widget gốc trừ khi một màn hình nhúng một component <WebView> thực sự.

Which locator to pick / Chọn locator nào

Inspector shows four options for almost every element: accessibility id, id, an android uiautomator selector, and xpath. For this app, only one of them is reliably safe.

Inspector hiển thị bốn lựa chọn cho gần như mọi phần tử: accessibility id, id, một selector android uiautomator, và xpath. Với ứng dụng này, chỉ có một lựa chọn thực sự đáng tin cậy.

StrategyVerdict
android=new UiSelector().resourceId(...)use this
id (resource-id)avoid
accessibility id (content-desc)avoid on dynamic elements
xpathlast resort only

android=new UiSelector().resourceId(...) is the one to use. It maps to the React Native testID, doesn't care about display text or language, and is already the pattern used in EventsPage.ts. The plain id strategy shows the same resource id string, but on this app it doesn't resolve: Appium's id strategy expects an Android resource id in package:id/name form, and these RN generated ids carry no package prefix. Accessibility id is usually the safer default in this framework, but on a dynamic element like an event card it resolves to content-desc, which here is the full display string (something like "Zenith Tour, Tokyo Night One at Tokyo Dome"), so it changes with the data and breaks under localization. Xpath is the fallback when nothing else is available: slowest to evaluate, and the first thing to break when the view tree shifts.

android=new UiSelector().resourceId(...) là lựa chọn nên dùng. Nó ánh xạ trực tiếp tới testID của React Native, không phụ thuộc vào chữ hiển thị hay ngôn ngữ, và cũng là mẫu đang được dùng trong EventsPage.ts. Chiến lược id hiển thị cùng chuỗi resource id đó, nhưng trên ứng dụng này nó không phân giải được: chiến lược id của Appium yêu cầu resource id ở dạng package:id/name, trong khi các id do RN sinh ra không có tiền tố package. Accessibility id thường là lựa chọn an toàn hơn trong framework này, nhưng với một phần tử động như thẻ sự kiện, nó phân giải thành content-desc, ở đây là toàn bộ chuỗi hiển thị (kiểu như "Zenith Tour, Tokyo Night One at Tokyo Dome"), nên sẽ thay đổi theo dữ liệu và gãy khi đổi ngôn ngữ. Xpath là phương án cuối khi không còn lựa chọn nào khác: chậm nhất khi Appium tính toán, và cũng là thứ đầu tiên gãy khi cây view thay đổi cấu trúc.

Running gestures from Inspector / Chạy cử chỉ (gesture) từ Inspector

Inspector has two ways to trigger a gesture. The Gestures tab builds a W3C action chain visually (pointer moves, downs, ups, pauses), which is exactly what utils/gestureHelper.ts sends through driver.performActions(). The Commands tab's Execute Methods list has mobile: swipeGesture, mobile: scrollGesture, and similar UiAutomator2 plugin shortcuts, useful for a quick check but not the same mechanism the helper uses.

The gesture files in docs/gestures/ were built from the eight methods in GestureHelper and validated against Inspector's own parser (gesturefile-parsing.js in the appium-inspector source) before being handed over, so they import without errors. Coordinates in the file format are percentages of screen size, which is what the helper already uses, except for the two pinch files: those convert a pixel offset from the original code against this session's device resolution (1080 by 2340), so they would need recalculating for a different screen. Import them from the Gestures tab, Import from File; the tool accepts several files at once, one gesture per file.

doubleTap() and scrollToElement() in the helper don't reduce to a single static gesture. doubleTap is two separate WebDriver clicks, approximated here as one chain with two down and up cycles. scrollToElement is a retry loop calling swipeVertical between visibility checks, which has no equivalent in a fixed action chain.

Inspector có hai cách để chạy một cử chỉ. Tab Gestures dựng một chuỗi hành động theo chuẩn W3C bằng giao diện trực quan (di chuyển con trỏ, nhấn xuống, nhấc lên, tạm dừng), đúng bằng cơ chế mà utils/gestureHelper.ts gửi qua driver.performActions(). Danh sách Execute Methods trong tab Commands có mobile: swipeGesture, mobile: scrollGesture và các lệnh tắt tương tự của plugin UiAutomator2, hữu ích để kiểm tra nhanh nhưng không cùng cơ chế với helper đang dùng.

Các file gesture trong docs/gestures/ được xây dựng từ tám phương thức trong GestureHelper và đã được kiểm tra bằng chính bộ phân tích của Inspector (gesturefile-parsing.js trong mã nguồn appium-inspector) trước khi bàn giao, nên import vào sẽ không lỗi. Tọa độ trong định dạng file này là phần trăm theo kích thước màn hình, giống với cách helper đang dùng, ngoại trừ hai file pinch: hai file đó quy đổi độ lệch pixel trong code gốc theo độ phân giải thiết bị của phiên này (1080 x 2340), nên cần tính lại nếu dùng trên màn hình khác. Import từ tab Gestures, chọn Import from File; công cụ cho phép chọn nhiều file cùng lúc, mỗi file là một gesture.

doubleTap() và scrollToElement() trong helper không thể rút gọn thành một cử chỉ tĩnh duy nhất. doubleTap thực chất là hai lệnh click riêng biệt của WebDriver, ở đây được mô phỏng gần đúng bằng một chuỗi gồm hai lần nhấn xuống và nhấc lên. scrollToElement là một vòng lặp thử lại, gọi swipeVertical xen giữa các lần kiểm tra hiển thị, không có gì tương đương trong một chuỗi hành động cố định.

  • docs/gestures/01-swipe-vertical-down.json swipeVertical(80, 20, 1000)
  • docs/gestures/02-swipe-vertical-up.json swipeVertical(20, 80, 1000)
  • docs/gestures/03-swipe-horizontal-default.json swipeHorizontal(80, 20, 1000)
  • docs/gestures/04-long-press.json longPress(element, 2000)
  • docs/gestures/05-tap-at-coordinates.json tapAtCoordinates(x, y)
  • docs/gestures/06-double-tap.json doubleTap(element), approximated
  • docs/gestures/07-pinch-out-zoom-out.json pinchOut()
  • docs/gestures/08-pinch-in-zoom-in.json pinchIn()
