Why not just use a free tier

This repo is private right now, and every device farm treats that differently. None of them hand out an ongoing free tier to a private project. What you get instead is a one-time pile of trial minutes, enough to prove the integration works, not enough to run on every week.

Make the repo public and apply for BrowserStack's open-source program, and that changes. Here's what each provider actually offers, private versus public.

Provider Private repo Public / OSS-qualifying
BrowserStack App Automate 100 min trial, one time Free for the life of the project: Live, Automate, and Percy with no cap, 5 users and 5 parallel sessions. Apply with just a name, an email, and the project URL.
LambdaTest 100 lifetime minutes, one time A grant of 10 parallel HyperExecute sessions plus unrestricted Test-at-Scale, but they check for a real license file and actual commit activity first.
Sauce Labs No documented ongoing free tier Still fuzzy even public. Their open-source page talks about giving back, not about a device-cloud grant, so this would mean emailing them and hoping.
AWS Device Farm 1000 device minutes, signup credit No change. There's no open-source program here, it's billed straight to the AWS account regardless of who can see the repo.
Firebase Test Lab Free daily quota, but doesn't apply Still doesn't apply. It runs uploaded Espresso or XCUITest packages, not an external Appium client, so our WebdriverIO setup has nothing to connect to.

BrowserStack is the pick. It has the cleanest WebdriverIO documentation of the three real contenders and the deepest device catalog. Worth applying to LambdaTest's grant too as a backup, but the config below is built around BrowserStack.

Three things only you can do

Each one is either identity-bound or hard to undo, so none of them happen automatically once this plan is approved.

  1. 01
    VISIBILITY

    Flip the repo to public

    Anyone who can currently see this privately loses that boundary, and it's not a change to make on someone else's behalf. Say the word and I'll run gh repo edit --visibility public, but I'll confirm with you again right before it happens.

  2. 02
    APPLICATION

    Submit the BrowserStack (and LambdaTest) forms

    These are tied to your name, your email, and the project URL. You should be the one submitting them, not me pretending to be you.

  3. 03
    SECRETS

    Add the real credentials to GitHub Actions

    Once trial or grant credentials exist, they go into Settings > Secrets and variables > Actions as BROWSERSTACK_USERNAME and BROWSERSTACK_ACCESS_KEY.

None of this has to happen before the code work starts. The 100-minute trial runs fine on a private repo, so everything below can be built and tested now. Going public and applying for the grant is a decision for whenever you're ready to commit to it.

What gets built

Same pattern the local configs already use: a new file per target, spread over the shared base config, no new abstraction layer.

  1. 01
    CONFIG

    Two new wdio configs

    config/wdio.browserstack.android.conf.ts and the iOS twin. Same shallow spread over baseConfig as the local files, but the appium service is swapped for the browserstack service, and capabilities move to the current bstack:options nesting instead of the flat legacy keys some older BrowserStack examples still show.

  2. 02
    SCRIPT

    An app upload helper

    BrowserStack needs the binary uploaded once per build to hand back a bs:// app ID, it can't just read a local path the way the local Appium configs do. scripts/uploadAppToBrowserStack.ts posts the file with Axios and prints the ID. A raw curl one-liner in package.json would have been simpler, but .env values are dotenv-loaded rather than real shell variables, so it wouldn't have resolved the credentials, and PowerShell and Bash disagree on syntax anyway.

  3. 03
    PACKAGE.JSON

    New scripts and one new dependency

    @wdio/browserstack-service at 9.33.1, the current version and peer-compatible with the @wdio/cli already pinned here. Plus test:browserstack:android, test:browserstack:ios, and the two upload scripts.

  4. 04
    ENV

    New variables in .env.example

    BROWSERSTACK_USERNAME, BROWSERSTACK_ACCESS_KEY, an app ID and a device name and OS version per platform. Defaults match what's already in .env for the local setup, a Pixel 7 on 13.0, an iPhone 14 Pro on 16.0.

  5. 05
    GITIGNORE

    .env stops being tracked

    Right now .env is committed to git, fine while it only held local paths and a VM IP. Once a real BrowserStack key lives in there on a public repo, that stops being fine. .env goes back into .gitignore, git rm --cached pulls it out of the index without touching the copy on disk, and .env.example keeps doing the job it already does.

  6. 06
    CI

    A new job in the GitHub workflow

    test-browserstack, running on ubuntu-latest since BrowserStack is the device and the Appium server both, no macOS runner or local emulator needed. It sits alongside test-android and test-ios rather than replacing them, the fast local Genymotion loop still earns its keep day to day.

  7. 07
    DOCS

    Two skill files get a new section

    running-mobile-tests-appium walks through signup, upload, env vars, first run. ci-release-triage gets the new job added to its diagram of what runs where.

  8. 08
    APPIUM-MCP

    Triage doesn't need Genymotion after this

    appium-mcp turns out to support two modes: an embedded local driver against adb, which is what's wired up today, and a remote WebDriver mode via a remoteServerUrl argument. Point that at the BrowserStack hub with the account's user and key in the URL, and appium-mcp can inspect a cloud session exactly like a local one, useful on this machine specifically since Genymotion isn't even installed here yet.

iOS stays blocked, and this plan doesn't fix it

Checked FrontRow's GitHub releases directly. The only iOS asset published is FrontRow.app.zip, a Simulator build for Apple Silicon, and the release notes say outright that it will not run on a physical iPhone. There's no .ipa anywhere upstream.

The repo does have an ios/FrontRow.xcworkspace, so a real .ipa could be built from source, but that takes a Mac, Xcode, and someone's own Apple Developer signing setup, none of which exist here. The BrowserStack iOS config gets written anyway, it just has nothing to run against until that build shows up.

How we'll know it worked

  • type-check and lint pass on the two new config files
  • git status shows .env as untracked but still present locally after the .gitignore fix
  • npm run browserstack:upload:android prints a real bs:// app ID
  • a smoke run against BrowserStack shows up in their dashboard and lands the same Allure results a local run would
  • once secrets are in GitHub Actions, the new CI job actually completes and its results merge into the existing report
  • appium-mcp attaches to a live BrowserStack session through remoteServerUrl and actually returns data
  • iOS stays marked unverified until a signed build exists, no claiming it works before then

Where this stands

Nothing above is committed yet. Once you're ready, the config files, the upload script, and the CI job get built and run against the trial account first, the public/OSS-grant path can come after.
